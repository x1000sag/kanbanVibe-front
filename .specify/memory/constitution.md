# KanbanVibe Frontend Constitution

## Core Principles

### I. Расширяемость

Границы API, домена и инфраструктуры MUST оставаться явными.
Домен Board, Column и Card MUST NOT зависеть от HTTP, CLI или способа хранения.
Публичный контракт и схема данных MUST меняться через версию контракта или миграцию.
Ломающее изменение без ADR и плана совместимости MUST NOT приниматься.
Одноразовый обход MUST NOT закрывать границу, у которой уже есть интерфейс
или точка расширения.
Feature flag SHOULD применяться, когда поведение нужно включать отдельно от выкладки кода.

В этом репозитории слои такие: типы домена (`src/types`), клиент HTTP
(`src/services`) как единственная сетевая граница, состояние (`src/stores`),
экраны (`src/components`, `src/views`). Компонент MUST NOT вызывать сеть
и MUST NOT читать хранилище браузера с токеном напрямую.

Обоснование: KanbanVibe — долгоживущий продукт. Смена хранения и авторизации
идёт через границы, а не через разовые правки.

### II. Надёжность

Критические пути MUST иметь тесты: авторизация, сохранение доски,
миграция клиентского состояния и запись состояния.
Ошибка MUST быть явной для вызывающей стороны. Тихая порча или потеря данных MUST NOT происходить.
Миграция контракта и клиентского состояния SHOULD быть обратимой.
Необратимая миграция MUST сопровождаться ADR и планом отката.
Auth MUST быть безопасным по умолчанию: секрет и токен не в репозитории и не в логе,
пароль MUST NOT сохраняться на клиенте.
Доступ к чужой доске и профилю MUST NOT предоставляться.
Сбой API MUST быть виден пользователю и MUST различаться по классу:
сеть, ошибка клиента (4xx), отказ сервера (5xx), отказ аутентификации.
Недоступность API MUST NOT выглядеть как пустая доска без ошибки.

Запись доски MUST выполняться только после успешного чтения актуального состояния
в этой сессии, кроме явно заданного сценария создания или сброса.

Пока npm-команды тестов нет, первое изменение критического пути MUST добавить
раннер и тесты этого пути. Кроме списка выше, критичны: ответ не-2xx,
валидация карточки (заголовок обязателен, теги уникальны), доступное имя
и клавиатура основных действий доски, а после появления входа — защита маршрута и 401.
Смена контракта MUST проверяться сценарием загрузка, правка, сохранение
против опубликованной схемы.

Обоснование: сбой хранения или auth бьёт по данным пользователя. Тесты и явная ошибка
делают отказ видимым до поставки.

### III. Функциональность

Спецификация MUST поставляться целиком, включая граничные случаи, пустые состояния
и ошибки. Демонстрационный срез не считается выполнением сценария.
Сообщение об ошибке MUST быть понятно человеку и MUST NOT раскрывать секрет.
Интерфейс MUST быть доступен с клавиатуры. У интерактивного элемента MUST быть
доступное имя. Статус MUST NOT сообщаться только цветом. Фокус MUST входить
в диалог и возвращаться к источнику.
Контракт API, конфигурация клиента и сценарии входа MUST быть документированы
для интегратора и оператора.
Поведение, которое видит пользователь, MUST быть согласованным на всех экранах.
Требования доступности интерфейса MUST выполняться в UI и MUST учитываться
в контракте API, от которого интерфейс зависит.

Обоснование: ценность продукта — законченный сценарий, а не частичный экран.

### IV. Консистентность доменной модели

Код, спецификации, ADR и документация MUST описывать одну модель: Board, Column, Card.
Пока спецификация не изменила модель, доска содержит колонки, колонка — карточки,
а карточка содержит id, title, необязательные description, tags и deadline, а также createdAt.
Имя колонки MUST быть уникальным в пределах доски.
Идентификатор карточки MUST быть уникальным. Теги одной карточки MUST быть уникальны.
Срок карточки, если задан, MUST использовать дату YYYY-MM-DD.
Время создания MUST храниться в UTC.
Изменение инварианта MUST проходить через спецификацию и ADR, а не через локальное исключение.

Имена полей JSON MUST совпадать с опубликованным контрактом.
Текущий контракт не задаёт позицию карточки внутри колонки. Позиция, удаление,
архив и поиск не запрещены конституцией: их добавляет спецификация и версия контракта.

Обоснование: CLI, API и Vue SPA читают одну модель. Расхождение артефактов ломает контракт.

### V. Spec-Driven Development

Новая функциональность MUST идти циклом Spec Kit:
constitution, specify, clarify, plan, tasks, implement.
План MUST содержать Constitution Check по принципам I–V до проектирования
и повторно после него.
Мелкая правка дефекта и правка документации MAY идти без новой спецификации,
если поведение продукта и контракт не меняются.
Реализация MUST соответствовать spec.md, plan.md и tasks.md фичи.
Смена поведения MUST обновлять spec.md фичи и опубликованный контракт
в том же изменении. Если для правила есть ADR, он MUST обновляться вместе с ними.

Обоснование: конституция и спецификация задают объём. Код не опережает их.

## Технологический стек и целевая архитектура

KanbanVibe — профессиональный продукт. Учебный прототип не задаёт норму качества.

Текущая база репозитория: Vue 3, Vite, TypeScript, Pinia.
Приложение живёт в корне репозитория, а не в каталоге `frontend/`.
Сейчас клиент читает и пишет доску через HTTP без сессии.
Это переходное состояние, а не норма продукта.

Целевая архитектура, которой MUST соответствовать новые спецификации:
Vue SPA, веб-API на .NET в репозитории kanbanVibe-Back, PostgreSQL,
учётная запись и JWT, одна доска на пользователя.
Файловое хранилище доски MUST NOT закрепляться как целевое
и MUST NOT быть источником истины клиента.
Черновик `specs/002-frontend-dev/contracts/api.yaml` действует, пока его
не сменит версия контракта. Упоминание файла `data/board.json` в черновике
не норма. Смена полей или кодов ответа MUST обновлять контракт в той же поставке.

Базовый URL MUST задаваться через `VITE_API_BASE_URL`.
Запасное значение в коде MUST совпадать с `.env.example` либо отсутствовать.
Расхождение запасного URL и примера MUST NOT сохраняться.

Клиент MUST быть готов к JWT. При наличии сессии запрос MUST нести Authorization.
Ответ 401 MUST трактоваться как отказ аутентификации, а не как обычный сбой сохранения.
Пока эндпоинт ещё анонимный, спецификация фичи MUST назвать это временным исключением.
Новый мутирующий сценарий MUST NOT закреплять анонимную запись как норму.

Язык артефактов — русский: конституция, спецификации и тексты интерфейса.
Идентификаторы кода следуют контракту API и стилю TypeScript.

## Правила поставки

Объём фазы MUST фиксироваться спецификацией. Дорожная карта задаёт направление
и MUST NOT подменять спецификацию и MUST NOT снижать планку принципов I–III.
Формулировки «достаточно для занятия», «минимальный MVP» и YAGNI MUST NOT быть основанием
пропустить тесты критического пути, явную ошибку, миграцию, версию контракта
или граничный случай указанного сценария.
Незапрошенная подсистема MUST NOT добавляться без спецификации.
Обратная совместимость опубликованного контракта MUST сохраняться,
пока спецификация или ADR явно не вводит версию и миграцию.
`npm run build` MUST проходить. Подавление ошибки типов ради демонстрационной
сборки MUST NOT приниматься.
Более простое решение SHOULD выбираться, когда оно выполняет принципы I–V.
Простота MUST NOT снимать тесты, явную ошибку, доступность и версию контракта.

## Governance

Конституция MUST иметь приоритет над README, ADR, спецификациями и AGENTS.md
при расхождении. Другие документы приводятся к ней, а не наоборот.
Поправка MUST проходить через /speckit.constitution, а не через правку шаблонов Spec Kit.
Версия SHOULD расти так: MAJOR — снятие или несовместимое переопределение принципа;
MINOR — новый принцип или существенное расширение правила; PATCH — уточнение без смены нормы.
Дата ратификации не меняется. Дата поправки — день принятого изменения.
Правка, которая меняет правила для агентов, MUST синхронизировать AGENTS.md,
если файл повторяет эти правила.
Ревью MUST проверять Constitution Check. Нарушение принципа MUST быть
явно обосновано в плане либо устранено до реализации.
Шаблоны .specify/templates/ MUST NOT редактироваться ради смены принципов:
их читает Spec Kit 1.2.3 в рантайме.
